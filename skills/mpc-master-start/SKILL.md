# MPC Master Start

## 概览

读取一个 GSD 计划文档或已经拆分好的任务列表，把任务整理写入 `<repo-root>/.mpc/mpc.md`。默认把输入文件视为 GSD 已拆分任务列表来源；如果源条目已经是可执行任务，优先保留其顺序、粒度和语义，只做规范化录入。只有当条目明显过粗、混合多个可分离工作、或无法被稳定跟踪时，才补做轻量拆分。

所有控制文件都固定放在当前项目的 Git 仓库根目录 `.mpc/` 下；即使从子目录触发，也要先解析到仓库根目录。只负责初始化控制文件、整理任务块、维护依赖关系和输出建议命令；不要代替子任务执行开发，也不要自动执行任何命令。

## 不可违背的约束

- 只把调用者提供的计划文件，以及现有 `<repo-root>/.mpc/mpc.md` / `<repo-root>/.mpc/mpc_archive.md` 当作事实来源。
- 在任何写入开始前先申请 `<repo-root>/.mpc/.lock.md`；锁存在时每 2 秒重试一次，最多等待 60 秒；锁超过 10 分钟未释放时停止并报告陈旧锁。
- 在锁文件中至少写入：当前 skill 名称、目标任务列表、当前仓库目录或分支、加锁时间。
- 获取锁后重新读取最新的 `<repo-root>/.mpc/mpc.md`；必要时同时读取 `<repo-root>/.mpc/mpc_archive.md`。
- 写入时只允许：
  - 追加新的子任务块。
  - 以最小改动范围更新直接前序任务的 `后序子任务`。
  - 更新文件头部 `最后更新时间` 与 `任务总数`。
- 不得重排、折叠、润色或重写无关任务块。
- 所有时间统一写成 `YYYY-MM-DD HH:mm:ss +08:00`。
- 所有空值字段必须保留并写成 `待填写` 或 `无`，不得省略字段。
- 使用“临时文件 + 原子替换”写回，不要原地覆盖。
- 无论成功或失败，只要持有过锁，都必须在结束前释放 `<repo-root>/.mpc/.lock.md`。

## 固定结构

始终按以下顺序创建每个任务块：

`任务标识 -> 状态 -> 来源计划文件 -> 执行模式 -> 执行目录 -> 前序子任务 -> 后序子任务 -> 子任务目标 -> 开始时间 -> 完成时间 -> 回归时间 -> 归档时间 -> 最后更新时间 -> 累计耗时 -> 预计剩余时间 -> 当前进度概况 -> 阻塞事项 -> 下一步提示词 -> 开始提示词 -> 完成提示词 -> 完成摘要 -> 回归摘要 -> 归档状态`

其中必须满足：

- `状态` 初始固定为 `未开始`。
- `执行模式` 固定写成 `single_dir`。
- `执行目录` 固定写成 `.`。
- `子任务目标` 必须写成带 `text` 信息字符串的 fenced code block，控制在 1 到 5 行，内容必须面向结果、可直接用于完成判定。
- `归档状态` 初始固定为 `未归档`。
- `阻塞事项` 初始写 `无`。
- 其他未确定字段写 `待填写`。

## 整理流程

1. 读取调用者提供的计划文件。
2. 判断源文档中的条目是否已经是 GSD 已拆分任务列表。
3. 如果条目已经可执行，保留其顺序、粒度和语义，只做规范化录入。
4. 如果条目明显过粗、混合多个可分离工作、或无法被稳定跟踪，再做轻量拆分。
5. 判断哪些任务可以并行，哪些必须串行。
6. 为每个子任务生成全局唯一的任务名。
7. 仅使用小写字母、数字、下划线命名任务；拒绝与 `mpc`、`mpc_archive`、`lock` 等保留名称冲突的名字。
8. 在新增前校验 `<repo-root>/.mpc/mpc.md` 与 `<repo-root>/.mpc/mpc_archive.md` 中都不存在同名任务。
9. 如果任务之间存在明显代码冲突、强顺序依赖、共享同一核心改动点，或命中以下任一场景，则拆成串行子任务，并显式写明 `前序子任务` / `后序子任务`：
   - 同文件
   - 同核心模块
   - 路由或注册表
   - 依赖清单
   - 生成产物
   - 共享导出面
10. 如果是向现有链路追加后续任务，只允许最小范围修改直接前序任务的 `后序子任务` 字段。

## 提示词生成规则

为每个新任务自动生成：

- `任务标识`
- `前序子任务`
- `后序子任务`
- `子任务目标`
- `开始提示词`
- `完成提示词`

生成提示词时遵守这些规则：

- `开始提示词` 首句必须以 `利用gsd skills的能力，实现需求：<当前子任务目标摘要>` 开头。
- 推荐模板：

```text
利用gsd skills的能力，实现需求：<需求摘要>。先确认边界与现状，再推进实现，并在过程中持续同步可用于更新 mpc.md 的进展信息。
```

- `完成提示词` 必须明确说明结论基于利用 GSD skills 推进后的产出。
- 推荐模板：

```text
基于利用gsd skills推进该任务后的产出，请确认是否已经满足需求：<需求摘要>；请给出完成依据、风险与是否可进入下一阶段的结论。
```

- `子任务目标` 用于让 `mpc-slave` 判断任务是否可以建议完成，应写成结果导向而不是过程导向。
- 不要把回归或归档职责提前塞给子任务。
- 下游 `mpc-slave` 自动生成或刷新 `下一步提示词` 时，也必须保留 `利用gsd skills的能力，实现需求：...` 这一前缀语义。

## 文件初始化

- 如果 `<repo-root>/.mpc/` 不存在，先创建项目内控制目录。
- 如果 `<repo-root>/.mpc/mpc.md` 不存在，创建骨架文件并写入 `# MPC 控制文件`、`## 元信息`、`版本`、`最后更新时间`、`任务总数`。
- 不要在本 skill 中主动创建 `<repo-root>/.mpc/mpc_archive.md`，除非实现上必须依赖它做重名检查且文件尚不存在；此时只创建最小骨架。

## 任务树与输出要求

- 写入完成后，按 `<repo-root>/.mpc/mpc.md` 与 `<repo-root>/.mpc/mpc_archive.md` 的并集生成最新任务树；如果归档文件不存在，可以忽略。
- `前序子任务` 与 `后序子任务` 在存在多个任务时，统一按 `、` 拆分；`前序子任务 = 无` 的任务视为根节点。
- 子节点顺序严格使用父任务 `后序子任务` 中的顺序；根节点顺序优先保持 `mpc.md` 中的原始顺序。
- 树状图字符统一使用 `├─`、`└─`、`│  ` 与 3 个空格缩进。
- 如果发现同名任务同时存在于活动区与归档区、循环依赖、缺失子任务、或同一子任务被多个父任务直接声明为后序任务，立即报告数据异常并停止。

执行完成后，向调用者输出：

1. `本次新增任务清单`
2. `最新任务树`
3. `首轮可执行任务与 /mpc-slave 命令`

其中：

- `本次新增任务清单` 必须覆盖本轮全部新增任务，按写入顺序列出至少：
  - `任务标识`
  - 1 行 `子任务目标` 摘要
  - `前序子任务`
  - `状态`
- 不能只列首轮可执行任务。
- 被前序子任务阻塞的新任务也必须出现在新增任务清单和任务树中。
- 仅为首轮可执行子任务输出建议执行的命令，格式使用：

```text
/mpc-slave <子任务名称>
```

- 明确提示每个首轮可执行子任务应在独立对话框中推进。
- 如果本次新增任务里没有任何首轮可执行项，明确输出“首轮可执行子任务：无”，并简要指出阻塞来自哪些前序任务即可。

## 禁止事项

- 不要自动执行任何建议命令。
- 不要修改已有任务的业务提示词，除非该任务是本次新增链路的直接前序任务，且只更新它的 `后序子任务`。
- 不要把“任务整理”实现成对整个 `mpc.md` 的重写。
